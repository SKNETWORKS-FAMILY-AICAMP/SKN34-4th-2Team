학생 챗봇 사전 준비·캐시 배치 설계 — 2026-10-12 KST

1. 확인 범위
refactor/calculation-rules의 배포 파일과 AWS SSM을 통해 실제 실행 컨테이너를 확인했다.
운영 설정·컨테이너·데이터는 변경하지 않았다. OpenAI 호출은 0회다.
현재 배포 이미지와 브랜치 최신 코드는 구분해야 한다.

2. 실제 운영 구조
브라우저 → CloudFront → Django EC2 → AI EC2 → OpenAI API
CloudFront 경로는 배포 문서/설정 근거이며 이번에 CloudFront API를 재조회하지 않았다.
Django/AI 프로세스, 연결 주소, 환경변수, 컨테이너 포트는 실행 상태를 직접 조회했다.

Django EC2: i-09af311c959d14cc4, running, t3.small
- Gunicorn 3 workers × 4 threads. CHATBOT_URL은 AI private IP의 8001 포트.
- Redis 7은 같은 EC2의 Docker 내부 redis:6379/0. 호스트 포트 공개 없음.
- AUTH_SESSION_BACKEND=redis. Celery worker도 이 Redis를 사용.
- nginx, api, worker, redis 실행. beat는 실행 목록에 없음.

AI EC2: i-07856cc9d2859e4e8, running, t3.small
- Uvicorn 2 workers. 호스트 8001 → 컨테이너 8000.
- AI 컨테이너만 실행. REDIS_URL 설정 없음.
- 양쪽 모두 LMS_CHATBOT_WARMUP 설정 없음. 이번 로그인 후 준비 기능은 운영 활성화 전.
- 메모리 단일 시점: AI 컨테이너 약 354.6 MiB, 호스트 가용 약 1.05 GiB.
  순간값이므로 피크 부하 용량을 보장하지 않는다.

3. 권장 배치 (아직 구현/배포하지 않은 제안)
Django EC2의 기존 Redis는 인증 세션·작업 큐 용도로 유지한다.
AI EC2에 chat-cache Redis 컨테이너를 추가하고 AI 워커 2개가 공동 사용한다.
Redis는 원래 메모리 기반 저장소다. 이번 선택은 각 Python 프로세스의 메모리와,
같은 서버 내 별도 Redis 프로세스의 메모리 사이에서 공유 방법을 선택하는 것이다.

로그인 → Django 응답 완료
       → 비동기 내부 HTTP 요청 → AI 워커 → DB/S3에서 서버 권한으로 데이터 준비
                                      → 같은 AI EC2의 chat-cache에 저장
질문   → Django 인증 → AI 워커 → 권한/버전 확인 → chat-cache 재사용 → 계산/답변

로그인 직후와 질문 요청 때의 Django→AI EC2 통신은 존재한다.
캐시 접근은 AI EC2 안에서 이루어진다. Django가 개인 집계를 다시 보관하지 않는다.
워커 A가 준비한 결과를 워커 B도 재사용할 수 있다.
정책 설명에 필요한 RAG 검색까지 모든 질문에서 생략하는 설계는 아니다.

4. 설정과 자원 경계
- 챗봇 전용 CHATBOT_CONTEXT_REDIS_URL을 신설한다.
  배포에서는 redis://chat-cache:6379/0을 명시한다.
  로컬 호환을 위해 미설정 시 기존 REDIS_URL을 사용하는 규칙을 문서화하고 테스트한다.
- 일반 REDIS_URL 전체를 변경하지 않는다. 다른 AI 기능의 캐시와 설정 영향 분리.
- chat-cache는 AI 전용 Docker 네트워크에 연결하고 호스트 ports를 게시하지 않는다.
- 캐시 데이터는 재생성 가능하므로 영속화(AOF/RDB) 없이 시작하는 안을 사용한다.
- 초기 실험안: Redis maxmemory 128 MiB, 컨테이너 한도 256 MiB,
  maxmemory-policy noeviction. 실제 피크와 메모리 오버헤드 측정 후 조정.
  메모리 부족 쓰기 실패는 원본 조회로 복구하고, TTL 만료 후 저장 재개를 검증한다.
- 기존 TTL 300초, 항목 128 KiB 상한 유지. 개인 데이터 별도 프로세스 L1 캐시 없음.
- Redis 장애는 챗봇 중단 사유가 아니다. 기존 원본 조회와 백오프를 유지한다.
- 운영 활성화는 최신 코드 이미지와 Redis 준비 후 양 서버에 기능 플래그를 적용한다.
  이번 검토에서 플래그, 운영 이미지, 네트워크 설정을 변경하지 않았다.

5. 정확성·개인정보
- 공통 데이터: 기수/정책/일정 버전별 재사용. 개인 출결 포함 금지.
- 개인 데이터: 서버 인증 UID/사용자 ID/기수/출결 버전/기준일로 분리.
- 조회 시 현재 권한·기수와 정책/출결/일정 변경 여부 확인을 유지한다.
- TTL만으로 권한 변경을 처리하지 않는다. 현재 DB 검증을 성급히 제거하지 않는다.
- 준비 전후 버전 확인, Redis NX 중복 준비 제한, 소유자 확인 후 잠금 해제 유지.
- 캐시 재시작이나 TTL 만료 후에도 기존 코드 계산과 동일한 답변 근거를 제공한다.

6. 구현과 검증 순서
A. Sol 구현: 전용 캐시 URL 지원 및 미설정 호환, AI Compose에 chat-cache 추가,
   메모리 제한/내부 네트워크/healthcheck, 배포 문서와 기능 OFF 기본값 유지.
B. 검증: 환경변수 우선순위, 다른 Redis 소비자 비영향, Compose의 호스트 비공개 확인.
C. 로컬 실제 Redis + AI 2 workers: A 준비/B 재사용, 동시 로그인 중복 방지,
   사용자 간 격리, 기수 변경/계정 비활성/정책·출결 수정/만료/장애 회귀검증.
D. 동일 데이터로 OFF/ON 준비시간·TTFT·전체 응답시간 분리 측정.
   현재 DB 권한/버전 확인 비용이 남으므로 캐시만으로 전체 속도 개선을 단정하지 않는다.
E. 메모리 부족·Redis 재시작 때 fallback과 복구, 로그에 개인 원문 미기록 확인.
F. 결과 확인 후 별도 운영 반영. 롤백은 플래그 OFF로 원본 조회 복귀.
   인증용 Redis를 삭제하거나 FLUSH하지 않는다.

추후 AI EC2를 여러 대로 늘릴 때는 각 호스트의 로컬 캐시가 분리된다.
그 시점에 중앙 Redis/관리형 Redis를 검토한다. 지금부터 추가 EC2를 만들 필요는 없다.
