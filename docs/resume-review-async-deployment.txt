Resume Review HTTP 504 correction — 2026-10-12

Cause and scope
CloudFront VPC origin read timeout is 120 seconds. The synchronous review request
waited for a whole LLM stage; recent Analyze runs exceeded 180–220 seconds.
This release separates HTTP polling from LLM execution. It does not optimize
model latency or alter writing/validation policy.

Implementation
The authenticated /api/resume-review endpoint accepts asyncAttempt. Existing
clients without it retain their synchronous contract. The request key includes
the authorized owner, resume and complete payload. Redis NX enqueues one Celery
job per attempt; polling returns progress without starting another LLM call.
The existing worker advances at most eight checkpoint stages, keeping the
canonical request ID and continuation. Existing PostgreSQL execution locks,
Writer, independent Verifier and rewrite limit remain in force. A verification
timeout remains pending; it is not promoted to READY. Worker failures surface
as retryable UI failures rather than a successful result.
The frontend polls every three seconds, shows stage and elapsed time, and only
accepts a verified/legacy-final response. Polls do not consume the stage limit.
Polling is bounded to 30 minutes; Redis records expire after one hour.

Limits and operations
This establishes completion without 504 for one actual initial review; it is
not a new evaluation of sentence quality or the entire question/answer journey.
Model latency remains substantial. The first optimization target is Analyze,
followed by verification context, without dropping required factual checks.
Async operation requires the existing Redis and Celery worker. For local
development, run a worker with the same environment/Redis as Django (Windows:
celery -A lms_server worker --pool=solo -l info). Restarting only the AI server
does not start the Django task worker. Worker restarts/Redis loss can still
require a manual resume; the AI's persisted checkpoints remain the authority.
No commit or push was performed for this change.
