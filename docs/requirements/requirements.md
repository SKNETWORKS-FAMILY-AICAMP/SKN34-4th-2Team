# PLAYDATA LMS PostgreSQL Redesign - Requirements

> 상태: Draft

## 설계 원칙
- 기존 Firestore 구조를 PostgreSQL로 1:1 복제하지 않는다.
- 실제 운영 프로세스를 기준으로 요구사항을 재정의한다.
- 현재 상태와 이력 데이터를 구분한다.
- 관계형 조회/무결성 관리 가치가 낮은 UI 구성 데이터는 JSONB 사용을 허용한다.
- 불필요한 표시용 중복값은 저장하지 않고 FK로 참조한다.
- 외부 시스템의 원천 데이터와 LMS에서 확정한 업무 데이터를 구분한다.

## 사용자 / 기수
- 사용자는 현재 역할을 하나만 가진다.
- 역할 후보: student, instructor, admin.
- 학생/강사는 현재 기수를 최대 하나만 가진다.
- 현재 기수는 users.cohort_id로 참조한다.
- 과거 기수 소속 이력은 별도로 관리하지 않는다.
- 역할 변경 이력도 별도로 관리하지 않는다.
- 출결/제출/평가 등 업무 이벤트는 필요 시 발생 당시 기수 정보를 보존한다.

## 좌석 배치
- 관리자는 기수별 현재 좌석 배치를 관리한다.
- 좌석 배치는 월 단위로 변경될 수 있다.
- 과거 좌석 배치 이력 자체는 핵심 요구사항이 아니다.
- 학생/강사는 현재 확정된 좌석 배치를 조회할 수 있다.
- 행/열/출입문/강사석/빈칸 등의 레이아웃은 JSONB로 저장할 수 있다.

## 교시별 착석 확인
- 강사/관리자는 교시마다 학생의 실제 착석 여부를 확인할 수 있다.
- 착석 확인은 최종 출결 상태와 별개의 업무 기록이다.
- 학생/날짜/교시 단위로 기록한다.
- 확인자와 확인 시각을 기록할 수 있어야 한다.
- 동일 학생/동일 기수/동일 날짜/동일 교시에 중복 기록되지 않아야 한다.
- 자리 확인 결과가 출결 상태를 직접 변경하지 않는다.

## 설문 · 제출 관리
- 일반 교육 과제(Assignment)와 동일한 개념으로 취급하지 않는다.
- 제출 항목은 관리자가 생성한다.
- 제출 항목은 기본적으로 특정 기수를 대상으로 하지만, 동일 항목을 여러 기수에 동시에 배포할 수 있어야 한다.
- 제출 항목의 예: 리소스 환급 결제 영수증, 설문조사, 위클리 체크, 기타 행정 제출물.
- 제출 요청에는 제목, 안내, 마감일을 설정할 수 있어야 한다.
- 제출 방식은 외부 Google Form에 한정하지 않고 내부 Form, 파일 업로드, 링크 제출 등으로 확장 가능해야 한다.
- 외부 Google Form을 사용하는 경우 Form URL, Notion 가이드 URL 등을 제공할 수 있어야 한다.
- 학생별 제출 여부를 확인할 수 있어야 한다.
- 외부 제출을 사용하는 경우 LMS 사용자와 제출 응답을 매칭할 수 있어야 한다.
- 현재 구현에는 personalEmail을 Google Form 응답 매칭에 활용하는 개념이 존재한다.
- 마감 이후 제출은 원칙적으로 허용하지 않지만, 실제 제출이 발생한 경우 late 상태를 판단할 수 있어야 한다.
- pending/submitted/late/overdue와 같은 상태는 가능한 경우 due_at과 submitted_at을 기준으로 계산한다.

## 일일 출결
- 실제 운영에서는 고용24의 비콘 기반 출결이 입실/퇴실/외출/조퇴 등의 원천 정보 역할을 한다.
- 현재 프로젝트에서는 고용24의 실시간 정보를 직접 연동하기 어렵기 때문에 예시 출결 데이터를 사용한다.
- LMS의 attendances는 학생별/날짜별 최종 일일 출결 상태를 보존한다.
- 현재 구현 단계에서 예시 데이터는 실제 고용24 원천 데이터와 구분할 수 있어야 한다.
- 향후 고용24 데이터 import/API 연동이 생기더라도 최종 Attendance와 원천 이벤트는 동일 개념으로 취급하지 않는다.
- 학생별 동일 날짜에 최종 일일 출결은 하나만 존재한다.
- 출결 이력은 발생 당시 cohort_id를 보존한다.
- 입실/퇴실 시각은 가능하면 timestamptz로 저장한다.
- 최종 출결 상태 후보: present / late / early_leave / absent / official_leave.
- 외출은 원천 이벤트/출결 이슈로는 기록될 수 있으나, 반드시 최종 일일 상태와 1:1 대응하지 않는다.

## 출결 이슈 제출
- 출결 Google Form은 일반 설문·제출과 별도 업무로 취급한다.
- 출결 이슈는 출결 이슈가 발생한 학생이 개별적으로 제출한다.
- 폼의 목적은 매니저가 지각/조퇴/외출/결석 등의 이슈를 파악하고, 병가/휴가 등 일반 지각이 아닌 사유의 증빙·서류 준비와 확인을 지원하는 것이다.
- Google Form 응답이 최종 Attendance 상태를 자동 확정한다고 가정하지 않는다.
- 학생은 특정 날짜에 발생한 출결 이슈와 사유를 제출할 수 있어야 한다.
- 이슈 유형 후보: late / early_leave / outing / absent / leave.
- leave의 세부 유형은 sick_leave / vacation / official / other 등으로 확장 가능하다.
- 제출된 출결 이슈는 매니저의 확인 및 최종 Attendance 판단의 근거로 활용할 수 있어야 한다.
- 출결 이슈 제출 기록과 최종 Attendance 기록은 동일 데이터로 취급하지 않는다.

## 기록실
- 기록실은 학생의 활동/성과 증빙 제출과 관리자의 검토를 위한 업무 영역이다.
- 실제 운영 기록 유형은 certification / study / blog / study_cert / precourse_quiz 다섯 가지다.
- 학생은 기록을 생성하여 제출한다.
- 관리자는 전체 기록을 조회하고 승인 또는 반려한다.
- 기록 승인/반려 권한은 관리자에게 있다.
- 반려된 기록은 기존 레코드를 수정·재제출하지 않고 새 기록으로 다시 제출한다.
- 한 기록에는 증빙 파일이 여러 개 첨부될 수 있다.
- 증빙 파일의 실제 바이트는 S3에 저장하고 PostgreSQL에는 파일 메타데이터와 storage key를 저장한다.
- 기록 유형별 상세 입력값은 서로 다르므로 공통 필드와 유형별 상세 데이터를 분리하여 관리한다.
- 승인된 기록은 마일리지 규칙의 입력이 되며, 조건을 충족하면 마일리지 적립이 자동으로 발생하는 것을 목표로 한다.
- 자동 적립의 원장은 mileage_transactions로 관리한다.
- 동일 기록 승인으로 마일리지가 중복 적립되지 않아야 한다.
- 운영상 승인 취소는 드물지만 마일리지 조정이 필요한 경우 별도 음수 조정 거래로 회수할 수 있어야 한다.
- 관리자는 마일리지 관리 화면에서 특정 학생의 마일리지를 수동 조정/회수할 수 있어야 한다.

## 성취도 평가
- 성취도 평가는 강사가 생성/수정/발행한다.
- 관리자는 성취도 평가를 조회할 수 있으나 생성/수정/채점 권한은 기본적으로 갖지 않는다.
- 평가는 단위기간별로 운영되며 학생은 평가당 1회만 응시한다.
- 학생은 평가의 응시 가능 기간 내에만 응시할 수 있다.
- 현재 문항 유형은 multiple_choice와 short_answer 두 가지를 사용한다.
- 평가 제출 시 객관식과 단답형은 자동 채점할 수 있어야 한다.
- 단답형은 의미상 정답이지만 표현 차이로 자동 오답 처리될 수 있으므로 강사가 최종 점수를 수정할 수 있어야 한다.
- 강사는 문항별 최종 점수와 채점 의견을 수정할 수 있어야 한다.
- 자동 채점 점수와 강사가 확정한 최종 점수를 구분하여 저장한다.
- 학생은 제출 직후 결과, 점수, 정답, 해설을 확인할 수 있다.
- 커리큘럼 범위를 기반으로 LLM이 문항 초안을 생성할 수 있어야 한다.
- AI 생성 문항은 즉시 발행하지 않고 강사가 검토/수정 후 발행한다.
- 잘못 출제한 평가를 고려하여 삭제 기능은 유지한다.
- 단, 이미 응시 기록이 있는 평가 삭제는 응시/채점 이력을 훼손할 수 있으므로 정책적 보호가 필요하다.
- 기본 정책은 응시 기록이 없으면 물리 삭제 가능, 응시 기록이 있으면 비활성화/폐기 상태 전환을 우선한다.

## 미확정 요구사항
- 리소스 환급 영수증의 승인/반려 절차
- 외부 Google Form 응답 자동 수집 방식
- 출결 이슈 검토 상태/승인 절차
- 고용24 출결 데이터의 향후 연동 방식
- 기록실 유형별 상세 JSON 스키마 최종 확정
- 마일리지 적립 규칙과 관리자 수동 조정 상세 제약
- 평가 폐기 상태명 및 응시 기록이 존재할 때의 삭제 UX
