# PLAYDATA LMS PostgreSQL Redesign - Requirements

> 상태: Draft

## 설계 원칙
- Firestore 구조를 PostgreSQL로 1:1 복제하지 않는다.
- 실제 운영 프로세스를 기준으로 요구사항을 재정의한다.
- 현재 상태와 이력 데이터를 구분한다.
- 외부 시스템의 원천 데이터와 LMS의 확정 업무 데이터를 구분한다.

## 사용자 / 기수
- 사용자는 현재 역할을 하나만 가진다.
- 역할 후보: student, instructor, admin.
- 학생/강사는 현재 기수를 최대 하나만 가진다.
- 현재 기수는 users.cohort_id로 참조한다.
- 과거 기수 소속 이력과 역할 이력은 별도로 관리하지 않는다.
- 출결/제출/평가 등 업무 이벤트는 필요 시 발생 당시 cohort_id를 보존한다.

## 좌석 배치
- 기수별 현재 좌석 배치를 관리한다.
- 좌석 배치는 월 단위로 변경될 수 있으나 과거 배치 이력은 핵심 요구사항이 아니다.
- 좌석 레이아웃은 JSONB로 저장할 수 있다.

## 교시별 착석 확인
- 강사/관리자는 교시마다 학생의 실제 착석 여부를 확인할 수 있다.
- 착석 확인은 최종 출결 상태와 별개다.
- 학생/기수/날짜/교시 단위로 기록한다.
- 자리 확인 결과가 Attendance 상태를 직접 변경하지 않는다.

## 설문 · 제출 관리
- 일반 교육 과제(Assignment)와 동일한 개념으로 취급하지 않는다.
- 제출 항목은 관리자가 생성한다.
- 한 기수 배포가 메인이지만 동일 항목을 여러 기수에 동시 배포할 수 있다.
- 외부 Google Form뿐 아니라 내부 Form, 파일 업로드, 링크 제출로 확장 가능해야 한다.
- 학생별 제출 여부를 확인할 수 있어야 한다.
- 제출 상태는 가능한 경우 due_at과 submitted_at으로 계산한다.

## 일일 출결
- 실제 운영에서는 고용24의 비콘 기반 출결이 입실/퇴실/외출/조퇴 등의 원천 정보 역할을 한다.
- 현재 프로젝트에서는 고용24 실시간 정보를 직접 연동하기 어렵기 때문에 예시 출결 데이터를 사용한다.
- attendances는 학생별/날짜별 최종 일일 출결 상태를 보존한다.
- 현재의 예시 출결 데이터는 실제 고용24 원천 데이터와 구분할 수 있어야 한다.
- 향후 고용24 연동이 생기더라도 원천 이벤트와 최종 Attendance는 동일 개념으로 취급하지 않는다.
- 동일 학생/동일 날짜의 최종 일일 출결은 하나만 존재한다.
- 입실/퇴실 시각은 가능하면 timestamptz로 저장한다.
- 최종 상태 후보: present / late / early_leave / absent / official_leave.
- 외출은 원천 이벤트/이슈로 기록될 수 있으나 반드시 최종 일일 상태와 1:1 대응하지 않는다.

## 출결 이슈 제출
- 출결 Google Form은 일반 설문·제출과 별도 업무다.
- 출결 이슈가 있는 학생이 개별 제출한다.
- 목적은 매니저가 출결 이슈를 파악하고 병가/휴가 등 일반 지각이 아닌 사유의 증빙·서류 준비와 확인을 지원하는 것이다.
- Google Form 응답이 최종 Attendance 상태를 자동 확정한다고 가정하지 않는다.
- 이슈 유형 후보: late / early_leave / outing / absent / leave.
- leave 세부 유형 후보: sick_leave / vacation / official / other.
- 출결 이슈는 최종 Attendance 판단의 근거로 활용한다.

## 미확정 요구사항
- 출결 이슈 검토/승인 절차
- 병가/휴가 증빙 파일을 LMS 내부에서 직접 업로드할지 여부
- 고용24 출결 데이터의 향후 연동 방식(API / 파일 import / 수동)
- 외부 Google Form 응답 자동 수집 방식
- 성취도 평가/기록실/마일리지 상세 규칙
