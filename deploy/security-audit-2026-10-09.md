# 배포 보안 점검 — 2026-10-09

> 이 문서는 조치 전 점검 기록이다. 이후 운영에 적용한 수정과 남은 항목은 [보안 조치 결과](security-remediation-2026-10-09.md)를 참조한다.

대상: https://d1zqs4mfabqpqs.cloudfront.net 및 연결된 Django·AI EC2, RDS, S3, IAM, ECR.

## 결론

기본 네트워크 접근 제한과 API 인증은 동작한다. 그러나 비밀번호 변경 정책 우회와 토큰 폐기 부재가 확인되어, 외부 공개 범위를 넓히기 전에 인증 보완을 권장한다. 이는 침해 사실을 확인했다는 뜻이 아니다. 이번 점검은 침해 사고 포렌식이나 모든 기능의 권한 검증을 대체하지 않는다.

이번 작업은 읽기 전용 점검이다. 운영 계정·DB·배포 설정은 변경하지 않았고, 정기 작업도 켜지 않았다. 실제 계정 로그인 시도, 비밀번호 추측, 대량 요청, 운영 파일 업로드를 하지 않았다.

## 우선 조치

### 1. 높음: 일반 프로필 수정으로 비밀번호 변경 정책 우회

- `lms_api/lms/commands.py:130`의 `op_update_profile`은 `password` 입력을 현재 비밀번호 확인이나 길이 검사 없이 해시하여 저장한다.
- 인증된 `/api/command` → `updateProfile` → 해당 함수로 연결된다. 학생의 다른 사용자 UID 수정은 거부하지만 본인 비밀번호는 빈 문자열까지 허용한다.
- `/api/password`의 8자 및 현재 비밀번호 검사를 우회한다. 탈취된 접근 토큰만 가진 공격자가 피해자 비밀번호를 바꿔 접근을 지속할 위험이 있다. 비인증 상태에서 타인의 비밀번호를 바꿀 수 있다는 의미는 아니다.
- 배포 이미지의 실제 함수를 AST로 추출하여 가짜 사용자·가짜 DB 커서로 실행했다. 빈 비밀번호 해시를 저장하며 해당 빈 문자열 검증도 성공했다. 다른 사용자 UID는 PermissionError로 차단됐다. 실제 DB 변경 없음.
- 조치: 일반 프로필 API에서 password·인증 상태 변경 필드를 제거하고 전용 비밀번호 변경/관리자 초기화 경로만 허용한다. 모든 변경 경로에 일관된 검증과 세션 폐기를 적용한다.

### 2. 높음: 갱신 토큰 재사용 및 로그아웃/비밀번호 변경 후 세션 폐기 부재

- `lms_api/lms/api.py:169` 갱신 API는 이전 refresh token을 폐기하지 않고 새 토큰을 발급한다. `:218` 로그아웃은 성공 응답만 반환한다.
- `lms_api/lms/jwt_auth.py`의 인증은 활성 사용자 여부를 DB에서 다시 읽지만 비밀번호 변경 시각/세션 버전/폐기 목록을 검사하지 않는다.
- 운영 설정 확인: 접근 토큰 15분, 갱신 토큰 7일. 이전 갱신 토큰의 만료 전 반복 사용이 가능하고 새 갱신 토큰도 발급되므로, 유출 후 위험이 최초 7일로만 제한된다고 볼 수 없다.
- 오프라인에서 동일한 가짜 refresh token으로 연속 두 차례 갱신과 로그아웃 뒤 재갱신을 재현했다. 비밀번호 변경 후 미폐기는 코드 검토 결과이며 실제 운영 계정으로 시험하지 않았다.
- 조치: 회전 시 이전 갱신 토큰을 원자적으로 폐기하고 재사용을 탐지한다. 로그아웃 시 해당 세션, 비밀번호 변경/관리자 초기화 시 기존 세션을 무효화한다. SimpleJWT 설정만 켜서는 현재의 사용자 정의 엔드포인트에 적용되지 않는다.

### 3. 높음: 로그인 시도 제한 부재와 계정 존재 여부 노출

- 로그인 실패가 미등록/비활성 이메일과 잘못된 비밀번호에 서로 다른 메시지를 반환한다(`lms_api/lms/api.py:120`). 사용자 존재 여부를 추정할 수 있다.
- 점검한 Django 인증 코드·미들웨어·배포 nginx 설정에 로그인 시도 제한이 없고 CloudFront에 WAF도 연결되지 않았다. 반복 요청 부하 시험은 하지 않았다.
- 조치: 계정 및 신뢰할 수 있는 클라이언트 IP 기준 시도 제한, 실패 응답 통일, 로그인 입력 길이 제한을 적용한다. nginx/애플리케이션에서 제한을 구현할 수 있으므로 유료 WAF 도입이 필수인 것은 아니다. 프록시 뒤 IP 식별 시 임의의 X-Forwarded-For 값을 신뢰하지 않도록 한다.

### 5. 중간: DB 복구 보호와 접근 경로 보완

- RDS 저장 암호화는 켜져 있으나 백업 보관 1일, 삭제 보호 OFF다. 침해나 실수 발견이 늦으면 복구 가능한 시점이 부족하다.
- PubliclyAccessible=true이나 DB 5432는 Django·AI 보안 그룹 및 지정된 4개 /32 IP에 제한되어 있다. 인터넷 전체에 DB 포트가 열려 있다는 뜻은 아니다.
- DB 기본 보안 그룹에는 동일 보안 그룹끼리 모든 프로토콜 허용 규칙도 남아 있다.
- 조치: 삭제 보호, 최소 7일 백업 보관 및 복구 시험을 권장한다. 팀의 로컬 DB 접속 요구를 확인하고 불필요한 /32와 기본 그룹 자기 참조 규칙을 정리한다. 즉시 비공개 전환하면 기존 로컬 접속이 끊기므로 별도 접근 경로 준비가 필요하다.
- [AWS 백업 보관 문서](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.BackupRetention.html).

### 6. 추가 보완 사항

- `/api/openapi.json`이 비인증 상태에서 200으로 API 구조를 제공한다. `/api/docs`는 404다. 스키마 공개 자체가 인증 우회는 아니지만 의도하지 않았다면 운영에서 비활성화한다.
- 기록 증빙 업로드(`lms_api/lms/api.py:1961`)는 10MB 및 MIME 허용 목록을 검사하나 파일 바이트를 검증하지 않는다. MIME 위조 방지 및 파일 종류에 맞는 파서 검증을 추가한다. 이 사실만으로 코드 실행이 가능하다고 판단하지 않는다.
- Django 컨테이너 사용자 설정이 비어 있어 기본 root로 실행되며, root filesystem은 쓰기 가능하다. privileged는 false다. 비특권 사용자·필요한 경로만 쓰기 허용으로 피해 범위를 줄인다.
- CloudFront 기존 표준 로그 설정은 OFF이고 조회된 CloudTrail trail은 없다. 별도 logging v2, CloudWatch 전송, CloudTrail Lake 구성은 확인하지 않았다. CloudTrail 기본 Event history까지 없다는 뜻은 아니다. 접근/인증 로그 보존 및 알림을 확인해야 한다.
- 현재 CLI 운영은 root 로그인 세션을 사용한다. 루트 MFA는 켜져 있고 루트 장기 액세스 키는 없다. 일상 배포 작업은 제한된 별도 관리/배포 역할로 전환을 권장한다.
