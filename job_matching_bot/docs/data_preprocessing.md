# 수집 데이터와 전처리

채용공고 추천봇이 쓰는 데이터가 어디서 오고, 어떤 단계를 거쳐 벡터 인덱스에 들어가는지
적는다. 숫자는 **2026-09-13 00:55에 시작한 야간 배치** 기준이다(`artifacts/nightly/2026-09-13-0055.json`,
`2026-09-13-0055_sync.json`, `artifacts/job_store.sqlite`). 이 두 파일은 같은 날 23:00 배치가 옛 이름
(`2026-09-13.json`)으로 덮어써서 로그에서 복원한 것이다.

수집 원본과 저장소는 레포에 올리지 않는다. `artifacts/`는 `.gitignore` 대상이고,
저장소 파일이 375MB라 GitHub 파일 한도(100MB)를 넘는다. 팀원은 매일 밤 올라가는
공유 파일(`job_store_share.sqlite.gz`, 약 31MB)을 받아 쓴다(`sharing/share_store.py`).

## 3. 데이터 구조

### 원본 레코드 (JSONL)

크롤러가 `artifacts/raw/details/<날짜>.jsonl`에 한 줄에 공고 하나로 쌓는다. 상세 페이지의
핵심 정보 표, 본문 텍스트, 해시태그, 목록에서 본 값(`list_item`)을 담는다.

### 저장소 `job_store.sqlite`

| 표 | 역할 |
|---|---|
| `jobs` | 정규화한 공고. 원문 전체와 추출한 조건, 두 지문(`content_hash`, `embed_hash`) |
| `job_tags` | 기술스택·필수/우대 기술·직무 키워드. 조건 검색용 |
| `list_seen`, `list_sweeps` | 목록 관측 기록. 사라진 공고 판정에 쓴다 |
| `list_jobs` | 상세를 받지 않는 대분류의 목록 정보. 공고 찾기 챗봇의 조건 검색만 읽는다 |
| `link_checks` | 상세 페이지를 열어 본 결과. 한 시간 안에는 다시 열지 않는다 |
| `runs` | 적재 실행 기록(신규·만료·삭제·벡터 수·오류) |

`jobs`의 주요 필드:

| 필드 | 뜻 |
|---|---|
| `job_id` | `SARAMIN-<rec_idx>`. 인덱스 문서 ID로도 쓴다 |
| `description` | 본문 전체. 첨삭 모듈이 이걸 읽는다 |
| `career_type`, `min_career_years` | 신입(ENTRY) / 경력(EXPERIENCED) / 무관(ANY), 최소 연차 |
| `education`, `region`, `employment_type` | 학력, 근무지, 고용형태 |
| `tech_stack`, `keywords` | 기업이 고른 태그를 기술 어휘와 직무 키워드로 나눈 것 |
| `required_majors`, `required_certifications` | 자격요건 구간에서 뽑은 전공·자격증 |
| `body_is_image` | 본문이 이미지뿐이라 텍스트 요건이 없는 공고 |
| `status`, `first_seen_at`, `last_seen_at`, `missing_runs` | 게시 상태와 관측 이력 |
| `embed_hash`, `indexed_embed_hash` | 지금 내용의 지문과 마지막으로 인덱스에 올린 지문 |

### 벡터 인덱스 (Pinecone `job-posting`)

| 항목 | 값 |
|---|---|
| 임베딩 | OpenAI `text-embedding-3-small`, 1536차원, cosine |
| 문서 | 공고 하나 = 벡터 하나. ID는 `job_id` |
| 임베딩 텍스트 | 요건 구간(주요업무·자격요건·우대사항)만 라벨을 붙여 이은 것 |
| 메타데이터 | 필터용 `regions`·`nationwide`·`career_type`·`min_career_years`·`education`·`employment_type`·`status`, 근거 표시용 기술 목록, 재정렬이 읽을 요건 원문 1,200자(`excerpt`), `embed_hash` |

## 4. 전처리 단계

`python -m job_matching_bot.sync` 한 명령이 아래를 순서대로 돈다. 단계마다 건수와
제외 사유를 세어 리포트에 남기므로 어디서 데이터가 줄었는지 추적할 수 있다.

```
원본 JSONL → ① 유효성 검사 → ② 중복 제거 → ③ 정규화 → ④ 본문 정제·요건 추출
→ ⑤ 저장소 반영(증분) → ⑥ 품질 판정 → ⑦ 변경 확인 → ⑧ 임베딩·적재
```

### 수집 단계에서 하는 정제 (`crawling/crawl_detail.py`)

- **HTML → 텍스트.** BeautifulSoup으로 본문 영역만 골라 줄 단위 텍스트로 뽑는다.
- **끊긴 단어 복원.** 사람인은 본문의 `script` 글자 사이에 HTML 주석을 끼워 넣는다
  (XSS 방지). 주석을 먼저 지우지 않으면 `JavaScript`가 `ja vasc ript`로 쪼개져 기술
  매칭과 인용 검증이 둘 다 실패한다.
- **표 펼치기.** `담당업무 | 자격요건 | 우대사항`을 머리글 행으로 둔 표는 글로 읽으면 머리글이
  먼저 몰려 나와 자격요건 구간이 비어 보인다. 머리글을 각 칸 내용 앞으로 옮긴다. 표본
  4,000건 중 57건이 이 때문에 자격요건 없이 지나가고 있었다.
- **이미지 본문 표시.** 본문이 이미지뿐이면 `needs_human_review`로 남긴다.
- **제외 직종.** 직종 태그가 **전부** 배달·운전이면 상세를 받지 않는다(`ingestion/excluded_roles.py`).
  `기사`가 붙은 태그는 전기기사 같은 자격증과 글자가 같아서 정규식 대신 명시 목록으로만 거른다.

### ① 유효성 검사 (`sync.validate`)

| 버리는 것 | 이유 |
|---|---|
| `source_job_id`가 없다 | 공고를 식별할 수 없다 |
| 본문도 조건표도 없다 | 정규화해도 쓸 값이 없다 |

2026-09-13: 입력 3,138 → 통과 3,138.

### ② 중복 제거 (`ingestion/record_files.latest_by_id`)

같은 공고를 여러 번 받은 줄은 **마지막 줄만** 쓴다. 줄마다 저장하면 수정 횟수만 올라간다.

### ③ 정규화 (`ingestion/saramin.py`)

출처별 파서가 공통 `Job` 스키마로 바꾼다. 조건은 목록의 조건 문자열을 쪼개지 않고
상세 페이지의 **핵심 정보 표**에서 읽는다(표본 15건에서 100% 채워져 있었다).

- 연속 공백을 하나로, `지도보기` 같은 표시용 문구를 걷어낸다.
- 기술 태그를 기술 어휘(`saramin_tech_vocab`)에 있는 것은 `tech_stack`으로, 나머지는 `keywords`로 나눈다.
- 제목에 `신입`·`인턴`·`경력무관`이 있으면 본문에 연차가 있어도 경력직으로 바꾸지 않는다.

### ④ 본문 정제와 요건 추출

| 모듈 | 하는 일 |
|---|---|
| `ingestion/requirement_sections.py` | 본문을 제목 줄 기준으로 잘라 주요업무·자격요건·우대사항 구간을 찾는다. "📋 자격요건", "이런 분을 찾습니다" 같은 변형 제목을 공고 3,100건을 훑어 모았다. 근무조건·복리후생·전형절차는 구간을 끝내는 제목으로 본다 |
| `ingestion/qualifications.py` | 자격요건 구간에서 전공 그룹·자격증·어학·병역 조건을 뽑는다. "관련 전공"처럼 경계가 흐린 것은 탈락 조건으로 쓰지 않는다 |
| `ingestion/detail_quality.py` | 이미지 플래그가 있어도 본문 텍스트가 800자 이상이거나, 300자 이상이면서 요건 제목이 있으면 텍스트 공고로 되돌린다 |

### ⑤ 저장소 반영 (`ingest.py`)

`job_id` 기준 증분이다. 이번에 받은 공고와 목록 관측 기록을 대조해 신규·갱신·변경없음·만료·삭제를 판정한다.

- **만료**: 마감일이 수집 기준 시각보다 이전.
- **삭제**: 끝까지 훑은 대분류에서 이틀 연속 안 보였고, 상세 페이지를 열어 봐도 닫혀 있다.
  목록에서 한 번 못 본 공고 12건을 열어 보니 8건이 살아 있어서, 목록만으로는 지우지 않는다.
- 차단 등으로 목록 수집이 중간에 끊긴 날은 **아무것도 지우지 않는다**.

2026-09-13: 신규 3,138 · 만료 4,870 · 삭제 1,482 · 미관측(상태 유지) 100.

### ⑦ 변경 확인 — 증분 인덱싱

`embed_hash`는 **임베딩 텍스트와 필터 메타데이터만**으로 만든 지문이다. 저장소의
`embed_hash`와 `indexed_embed_hash`가 다른 공고만 다시 임베딩한다. 판정에 Pinecone 조회가 없다.

원본 전체 해시(`content_hash`)를 기준으로 삼지 않는 이유는 수집 시각·조회수처럼 매칭과
무관한 값이 바뀌어도 해시가 달라져, 다시 받은 공고를 전부 다시 임베딩하게 되기 때문이다.
마감일도 지문에서 뺀다. 마감은 다시 올리는 게 아니라 인덱스에서 지우는 것으로 처리한다.

2026-09-13: 인덱스에 이미 있음 21,212(임베딩 비용 0) · 올릴 것 2,415 · 지울 것 599.

### ⑧ 임베딩과 적재 (`retrieval/upsert.py`)

- 100건씩 묶어 임베딩하고 묶음마다 upsert한다. 중간에 끊겨도 진척이 남는다.

## 5. 설계 판단

**청킹을 하지 않는다.** 임베딩 텍스트가 요건 구간만이라 문서 중앙값이 500자 안팎이다.
공고 하나를 쪼개면 "자격요건"과 "우대사항"이 다른 벡터로 갈라져, 한 공고의 조건을 한 번에
대조할 수 없다. 본문 전체를 넣게 되면 그때 청킹을 붙인다.

**요건 구간만 임베딩한다.** 처음에는 본문 앞의 분류 경로 줄(`IT개발·데이터 > 직무·직업 >
백엔드/서버개발`)까지 넣었다. 이 줄이 모든 공고를 서로 비슷하게 만들어 유사도가
0.37~0.50에 뭉쳤다. 빼고 나서 검색이 공고를 구분하기 시작했다.

**메타데이터에 요건 원문 1,200자를 담는다.** 재정렬 LLM이 이 값을 읽는다. 300자로
잘랐을 때는 자격요건이 잘려 적합도가 전부 "보통"으로 나왔다. 1,200자면 공고의 88%가
온전히 들어가고, 메타데이터가 4KB 안이라 Pinecone 한도(40KB)에 여유가 있다.

**지역은 시·도 배열로 넣는다.** Pinecone은 문자열 부분 일치를 못 한다.
"서울 영등포구, 경기전체"를 `["서울", "경기"]`로 넣어 두고 `$in`으로 거른다. 전국 근무
공고는 `nationwide`로 따로 표시해 어느 희망 지역에서든 잡히게 한다.

## 7. 한계

- **출처가 하나다.** 사람인만 수집한다. 다른 사이트는 수집기도 파서도 없다.
- **이미지 본문 공고는 요건을 못 읽는다.** 19%가 이미지뿐이고 대부분 인덱스에서 빠진다. OCR은 하지 않는다.
- **기술 정보가 없는 공고가 많다.** 72%가 태그가 없다. 추천은 태그가 없으면 요건 구간 글에서 같은 어휘로 기술을 찾는데, OPEN 공고 31,874건 기준으로 태그·요건에서 30%, 글에서 17%를 얻고 54%는 여전히 기술 정보가 없다. 이런 공고는 기술 겹침 순위에서 제자리에 둔다. LLM 요구역량 추출을 켜면 글 본문 공고의 90%에서 기술을 얻는다(표본 200건, 요건 구간 사전 매칭은 23%). 하지만 이름이 사전과 맞지 않는 것이 72%이고, 하룻밤 신규분에 약 850만 토큰이 들어 꺼 두었다([modules.md](modules.md) coach/).
- **신입·경력을 함께 뽑는 공고는 경력 조건을 한 값으로 못 정한다.** 메타가 `경력무관`이고 요건이 경력을 요구하면 경력직으로 바로잡지만(위 규칙), 같은 요건에 "신입"도 있으면 그대로 둔다. 이런 OPEN 공고가 526건이다. 메타가 `경력무관`인데 요건 밖(우대사항 등)에만 "경력자"가 있는 공고는 경력 요구가 아니라서 바꾸지 않는다.
- **상세를 하룻밤에 다 받지 못한다.** 2026-09-13에는 신규 8,544건 중 3,138건만 받았다. 나머지는 다음 밤에 이어서 받는다.
