# 이력서 첨삭 v3 — 공고 요건 대화형 첨삭

v2 계약([resume-review-v2.md](resume-review-v2.md))은 그대로 두고 응답에 칸을 더했다. 기존 앱은 새 칸을 몰라도 동작한다.

## 무엇이 바뀌었나

| | v2 (resume-v11) | v3 (resume-v12 + 요건 대조) |
|---|---|---|
| 모델 출력 | 요약·문장 수정안·질문 + 섹션 진단·7개 기준 진단·STAR 점검 | 요약·문장 수정안·질문·**요건 판정**. 앱이 쓰지 않던 진단 셋을 뺐다 |
| 공고 사용 | 공고 원문을 통째로 넣음 | 공고를 **요건 목록**(필수·우대·주요 업무 + 공고 원문 인용)으로 정리해 넣음. 공고당 한 번, Firestore `jobRequirementProfiles`에 저장 |
| 대화 순서 | 모델이 준 순서, 자기소개서 틀 질문이 맨 앞 | 서버가 단계를 매겨 정렬: ① 문장 다듬기(앱이 한 카드로 묶어 한 번에 적용) ② 공고 요건 확인(최대 4개) ③ 경험 보완 ④ 지원동기 ⑤ 자기소개서 |
| "없음" 답 | 재첨삭을 한 번 돌림(약 10초) | 모델을 부르지 않고 기록만(`telemetry.model_skipped = none_answer`). 요건이면 `absent` |
| 숫자 검증 | `1.2s`와 `1.2초`를 다른 숫자로 봄 | 값과 단위로 비교. 단위가 달라지면(초→분) 여전히 보류 |
| 기술어 검증 | `ECS+GitHub`를 한 단어로 봄 | `+`·`/`로 이어 쓴 이름을 나누고, 숫자에 붙은 단위는 기술어에서 뺌 |
| 답변 근거 수정 | 원문에만 견줘 "팀원과 함께"를 본인 범위로 바꾸면 보류 | 답변이 본인 범위를 밝혔으면 허용. 지원동기는 공고 업무를 회사 맥락으로 쓸 수 있음 |
| 질문 중복 | 글자가 같을 때만 거름 | 같은 항목에서 비슷한 질문(유사도 0.57↑), 답한 질문을 표현만 바꾼 질문, "없음"이라고 적힌 질문을 거름 |
| 직무명 | "공공 SI 사업 Java 개발자 (신입)" | 모집 조건 괄호를 뗌: "공공 SI 사업 Java 개발자" |

## 응답에 더한 칸

```jsonc
{
  "requirement_map": [
    {"id": "req-1", "group": "must", "label": "Spring Boot 3.x 이상",
     "posting_quote": "Spring Boot 3.x, JDK 17 이상 사용 경험",
     "status": "unconfirmed",          // met · partial · unconfirmed · absent
     "evidence_paths": [], "evidence_quotes": [],
     "source": "none"}                  // resume · answer · user · none
  ],
  "questions": [{"...": "...", "requirement_id": "req-1", "stage": 2}],
  "sentence_reviews": [{"...": "...", "edit_type": "clarity", "requirement_id": null, "stage": 1}]
}
```

- `met`/`partial`은 이력서 원문이나 확인 답변의 **연속 인용이 실제로 있을 때만** 남는다. 인용이 없으면 서버가 `unconfirmed`로 낮춘다.
- 사용자가 "없음"이라고 답한 요건(`absent`)이나 답변으로 확인한 요건은 이후 판정이 덮지 않는다.
- 점수·등급은 만들지 않는다.

## 검증 방법

`evaluation/review_eval.py`가 목업 이력서로 대화 전체를 돈다. 첫 첨삭 → 질문마다 답변 → 그 항목 재첨삭 → 누락 점검. 첨삭 코드는 그대로 쓰고 Firestore만 메모리로 바꾼다.

- 답변은 "지원자 역할" 모델이 케이스의 `facts`(실제로 한 일)와 `not_done`(해 본 적 없는 것)만 보고 쓴다. 그래서 수정안에 이력서·답변에 없는 숫자·기술어가 나오거나 `not_done`이 새어 들어가면 지어낸 것이다.
- 요건 판정은 사람이 매긴 `expected_requirements`와 이름이 가장 비슷한 것끼리 견준다. 가장 위험한 틀림은 근거 없는데 `met`으로 본 것(over-claim)이다.
- **개발용**(`fixtures/review_cases_dev.json`, 8케이스)으로 고치고, **최종 확인용**(`review_cases_heldout.json`, 5케이스)은 고친 뒤 한 번만 돌린다. 고칠 때 본 케이스로 다시 재면 항상 좋아 보인다.

```
cd cover_letter_rag
python -m evaluation.review_eval --cases dev --label <이름>
python -m evaluation.review_eval --cases heldout --label <이름>   # 고치기를 마친 뒤에만
```

### 문장 다듬기 묶음 적용 (resume-v14)

수정안이 7개로 늘자, 앱이 수정안을 하나씩 모두 넘겨야 질문으로 가서 공고 요건 질문이 뒤로 밀렸다. 새 사실이 없는 표현 수정(맞춤법·문체·가독성)을 첫 첨삭에서 한 카드로 묶어, 고른 것만 한 번에 적용한 뒤 질문으로 넘어간다. 단계 번호도 이 순서에 맞춰 문장 다듬기를 1로 옮겼다.

- 적용은 기존 회사명·직무명 카드와 같은 묶음 경로(`selected_indices` 여러 개)를 쓴다. 되돌리기도 묶음 단위다.
- 적용하면 서버가 첨삭 결과를 새 이력서 버전으로 옮긴다(`rebase_review_response`). 이후 답변 재첨삭은 다듬어진 최신 문장 위에서 이어진다.
- 답변에서 해 보지 않았다고 한 부분을 "○○ 경험은 없지만"처럼 이력서에 옮겨 적지 않도록 지시문에 적었다(v13 측정에서 지원동기 수정안 한 건이 그렇게 썼다).

평가 도구의 `--apply-polish`가 이 흐름을 흉내 낸다(서버의 `build_application`·`rebase_review_response`를 그대로 쓴다).

묶음 적용 흐름으로 재 보니 사실 답변 반영이 28/35로 떨어졌다. 원인은 이름 없는 질문이었다. 서버가 한 줄짜리 프로젝트 설명에 붙이는 "이 프로젝트에서 해결하려던 기존 문제는?"이 어느 프로젝트인지 밝히지 않아, 답변이 다른 프로젝트 이야기로 가서 수정안이 나오지 않았다. 질문에 항목 이름("'LMS 출결 관리 서비스' 프로젝트에서…")을 넣고, 모델 질문에도 이름을 넣으라고 지시문에 적었다(resume-v15).

## 지원 자격 거르기 + STAR 판정 (resume-v16, 2026-09-15)

앱에서 "신입 또는 경력 2년 이하"를 요건 질문으로 받아 "2년 이하임"이라고 답했더니 쓸 문장이 없어 실패 문구가 떴다. 행동·결과가 이미 적힌 항목을 다시 파고드는 질문, 짧기만 하면 붙는 틀 질문, 특정 항목을 지목하는 기술 질문도 있었다.

| 바뀐 것 | 내용 |
|---|---|
| 요건 종류 | 요건 이름으로 `kind`를 가른다: `skill` / `eligibility`(경력 연수·학력·전공·병역·면허·근무 조건). 규칙이라 저장된 요건에도 매번 다시 적용한다. SQLite `jobs`의 `career_type`·`min_career_years`·`education`을 근거 문구로 붙인다(`snapshot_hash`에는 넣지 않는다). 지원 자격은 질문하지 않고 요건 줄에 "확인만"으로 따로 보인다 |
| "없음" 답 | 근거를 못 찾은(unconfirmed) 요건만 해당 없음(absent). 일부 근거가 있는(partial) 요건의 좁은 질문에 없다고 해도 표는 그대로 |
| STAR 판정 | 첫 첨삭에서 모델이 경험 칸(프로젝트·경력·교육·수상·활동 설명, 자기소개·도전·성장·장단점)마다 요소별 핵심 구절을 인용한다. 인용이 원문·확인 답변에 있을 때만 "있음". 후속 첨삭은 모델을 다시 부르지 않고, 답변이 내용 수정안에 반영됐으면 그 질문이 묻던 요소만 "있음"으로 바꾼다. 응답 `star_checks[]`: `field_path, present, missing, quotes, reason` |
| 질문 거르기 | 요건과 무관한 경험 질문 중 묻는 요소가 이미 있거나 행동·결과가 모두 있는 항목의 질문을 버린다. 근무 가능·지역·경력 인정 같은 조건 질문, 지원 자격·근거 없는 주요 업무에 붙은 질문도 버린다. 틀 질문은 행동·결과가 없는 문항에만, 공고 맞춤 첨삭은 경험 문항에 두 개까지. 한 줄 프로젝트 설명에 붙이던 질문도 행동·결과가 있으면 붙이지 않는다 |
| 질문 문구 | 기술 요건은 특정 항목을 지목하지 않고 "이력서의 어느 항목에서… 항목 이름과 함께"로 묻는다. 답의 항목 이름은 프로젝트·경력·교육·수상·활동에서 이름 일부로 찾는다 |
| 내부 용어 | 질문·이유·요약·수정 이유의 `projects[0].description`, `field_path`, "필드 경로"를 항목 이름으로 바꾼다 |

평가 도구에 지표를 더했다: 지원 자격 질문, 행동·결과가 이미 적힌 항목에 대한 질문(기대 STAR에서 행동·결과가 모두 있는 칸에 요건과 무관하게 붙은 질문), 헛답(사실을 답했는데 수정안도 요건 변화도 없는 턴), 내부 용어, STAR 판정 일치. 기대 STAR(`expected_star`)는 Claude가 원문만 읽고 매긴 값이라 사람 라벨이 아니다. 상황·과제는 경계가 애매해 참고로만 본다. 옛 기록은 `--rescore`로 같은 지표를 다시 셌다(STAR 판정은 없음).

목업 공고에는 지원 자격 줄이 거의 없어 개발용으로는 자격 질문이 0이었다. 그래서 인물·답변은 개발용 그대로 두고 공고만 자격 조건 공고로 바꾼 확인용 2케이스(`review_cases_probe.json`)를 따로 만들었다. 옛 코드로는 돌리지 못해 전후 비교는 없다.

## 답의 사실 잃지 않기 · 규칙 정리 (resume-v16p, 2026-09-15)

- 사실과 "없다"가 섞인 답: 예전에는 답에 "없어요"가 한 번만 있어도 대체 수정안이 답 전체를 버렸고, 모델도 답 전체를 없음으로 보고 수정안을 내지 않았다(v16m Node 장단점). 대체 수정안은 없다고 한 문장만 빼고 나머지 사실 문장으로 만든다. 후속 첨삭 범위 안내에 `prompts.MIXED_ANSWER_RULE`을 붙인다(첫 첨삭 지시문은 그대로).
- 답에 다른 항목 이름이 나올 때: 후속 첨삭은 답한 항목만 모델에 보여 줘서 "LMS에서 X, 숙소 예약 클론에서도 Y"의 Y가 사라졌다. `mentioned_item_answers`가 항목 이름이 분명히 나온 문장만 골라 그 항목의 답으로 붙인다(항목 2개까지, 저장하지 않음). 모델은 그 항목도 보고 고칠 수 있고, 근거 검증은 그 항목에 그 문장만 근거로 준다. 응답 `answer_scope_paths`에 함께 고칠 수 있었던 칸을 싣고, 앱은 답한 칸 수정안 다음에 그 칸 수정안을 보여 준다.
- 규칙 정리: 경험 칸 정규식(7곳), 칸 이름표(2벌), 항목 이름 키(2벌), 역할 과장 낱말(2벌), 이름 낱말·부정 표현 목록을 `app/review_rules.py` 한곳으로 옮겼다. 동작은 바꾸지 않았다(시험 207건 그대로 통과). 문장 나누기 함수 셋(`_sentences`·`_split_sentences`·`_split_answer_sentences`)은 최소 길이와 기준이 달라 그대로 뒀다.

### 확인 (v16p, 개발용 8 + 한 번도 안 본 unseen2 5) → v16q

끝나는 기준을 먼저 정했다: 사실이 사라지거나 엉뚱한 항목에 들어가거나 지어낸 것이 들어가면 고치고, 나머지는 남은 한계로 적는다.

| 항목 | 개발용 8 (v16n → v16p) | unseen2 5 (v16p, 한 번) |
|---|---|---|
| 사실 답변 반영 | 28/29 → 30/30 | 19/20 |
| 헛답 · 이미 적힌 칸 질문 | 0·3 → 0·3 | 1·2 |
| 지어낸 숫자·기술어 · 요건 over-claim | 0 · 0 | 0 · 0 |
| 요건 판정 일치 | 40/45 → 39/45 | 29/30 |
| STAR 행동·결과 과대 | 8 → 7 | 6 (과소 8) |
| 첫 첨삭 / 재첨삭 | 55.7초·7.7초 → 47.8초·9.2초 | 51.8초·11.4초 |
| 명사형 문장 잇기 | 26/30 → 25/30 | — |

unseen2: 답에 다른 항목 이름이 나와 함께 고친 칸이 생긴 턴 7, 그 칸 수정안 9개 모두 살아남음. 사실과 "없다"가 섞인 답 2턴 중 1턴에서 수정안이 나왔다(나머지 1턴은 답 사실이 원문 되풀이라 버려진 정상 경우). 새 프로젝트 제안 1.

기준에 걸린 결함 1건(v16q에서 고침): 교육 칸 질문에 회사 프로젝트에서 한 일을 답하자, 그 문장이 프로젝트 칸에 올바르게 들어가면서 교육 설명 수정안에도 들어가 교육 과정에서 한 일처럼 읽혔다. v16p가 떼어 낸 문장을 질문한 칸의 근거에도 그대로 남겼기 때문이다.
- 떼어 낸 문장은 질문한 칸의 모델 입력·근거에서 뺀다(`without_mentioned_sentences`). 저장하는 답은 그대로다.
- 그래도 질문한 칸 수정안에 그 항목 이름이 새로 들어가거나 떼어 낸 문장과 비슷한 문장(유사도 0.6 이상)이 있으면 `moved_to_other_item`으로 빼고 묻지 않는다(`withhold_moved_sentences`).
- unseen2로 찾은 결함이라 v16q 확인에 unseen2를 다시 쓰지 않는다.

## 고친 뒤 재첨삭 (앱, 2026-09-15)

사용자가 첨삭을 마친 뒤 이력서에 내용을 더 넣고 "재첨삭"을 누르는 흐름. 예전에는 마친 대화가 그대로 복원돼 입력창이 잠기고, 고친 이력서로 새 첨삭을 시작할 수 없었다(질문에 답하면 옛 판이라 `resume_version_changed`).

- 첨삭 시작 때 저장된 대화가 마친 것이거나 그 판(`input_hash`)이 지금 이력서와 다르면 대화를 정리하고 처음부터 첨삭한다. 맨 위에 "이력서를 처음부터 다시 첨삭했어요. 지난 대화는 정리했어요."를 붙인다.
- 목록에서 마친 대화를 열면 완료 안내에 "이력서를 고쳤다면 다시 첨삭" 버튼이 있다. 마치지 않은 대화를 열었는데 판이 달라졌으면 대화를 정리하고 첨삭 시작 화면으로 돌린다.
- 지난 대화에서 확인한 답은 새 첨삭에 넘기지 않는다. 사용자가 이력서에 직접 넣은 내용은 새 첨삭이 원문으로 본다.

### 사실 흐려짐 검사 · STAR 결과 종류 · 해 보지 않은 말 (resume-v16u ~ v16w)

- STAR 판정에 `result_kind`(수치 변화·상태 변화·검증·수상/선정·한 일·배운 점·계획)를 받아 앞의 넷만 결과로 인정한다. 낱말 목록이 아니라 모델 분류라 처음 보는 표현에도 쓸 수 있다. 첫 첨삭 41.7초로 느려지지 않았다.
- 후속 첨삭 내용 수정안 중 변경 폭 0.15 이상(턴당 4개)을 검사 모델(`app/fact_check.py`, reasoning low)에 동시에 물어, 원문에 한 일·결과로 적힌 구절이 빠지거나 목적·계획·참여·학습 표현으로 약해지면 `fact_notice`를 붙인다. 모델이 적은 구절이 원문에 있을 때만 붙이고 막지 않는다. 개발용 v16w: 검사 34번 평균 1.2초·최대 7.4초, 재첨삭 10.9초.
- 답을 원문 뒤에 "또한…" 문단으로만 붙이면 `flow_notice`. 후속 첨삭 안내에 `ANSWER_FLOW_RULE`.
- unseen4(v16u, 한 번)에서 기준 결함 1건: "개념만 배웠고 써 본 적은 없다"는 답에 핵심역량 수정안이 원문 문장을 지우고 그 말을 적었다. 수정안에 원문에 없던 해 보지 않았다는 말(`ABSENCE_STATEMENT`)이 들어가면 `absence_written`으로 보류한다(v16v). 변경 폭 0.245라 검사 모델 대상에서도 빠져 기준을 0.3 → 0.15로 낮췄다.
- 개발용 v16v에서 v16q의 "다른 항목 이야기 보류"가 자기소개서 수정안까지 막았다. 자기소개서·핵심역량은 경험을 가리키며 쓰는 칸이라, 이 보류와 근거 빼기는 경험 칸에 답했을 때만 한다(v16w).
- 개발용 v16w: 사실 답변 반영 28/28, 헛답 0, 지어낸 것·해 보지 않은 것 적기·요건 over-claim 0, 명사형 잇기 30/30, STAR 행동·결과 85/96(과대 6), 첫 첨삭 42.1초.

## 사람 말투 답으로 마지막 확인 (unseen5, v16w → v16x)

지원자 역할 모델이 사람처럼 답하게 했다: 짧게, 항목 이름 줄여 부르기(11턴), 다른 항목 섞기(10), 확신 없는 말(7), "그건 안 해 봤어요" 꼬리(6), 오타(3). 새 5케이스 29턴을 v16w로 한 번 쟀다.

- 막힌 턴 0, 지어낸 숫자·용어 0, 해 보지 않은 일 새어 들어감 0, 요건 28/28(과대 1), 사실 답 반영 27/28, 다듬기 23/23, 헛답·이미 적힌 칸 질문·내부 용어 0, STAR 행동·결과 66/80(과대 11). 첫 첨삭 42.6초, 후속 평균 14.2초, 검사 모델 36번 평균 1.5초.
- 기준 결함 2건(29턴 중 2턴, 확신 없는 답 7턴 중 2턴): "잘 모르겠는데 아마 ~했던 것 같아요"로 답한 테스트 개수와 작업이 단정문 수정안이 됐다. 서버 검사에 걸리지 않았다.
- 경계 1건: 답을 그대로 붙이는 대체 수정안에 채팅 말투("붙였어요")와 "만들어 보지 않았어요"가 들어갔다. `ABSENCE_STATEMENT`가 써·사용해·다뤄·적용해만 봤다.

v16x에서 고친 것:

- 답을 문장(과 "것 같고"·"것 같은데" 뒤)으로 나눠 확신하지 못한 문장(`UNCERTAIN_STATEMENT`: 것 같·아마·확실/정확하지 않·기억이 안 나·헷갈)을 확인된 근거에서 뺀다(`split_uncertain_answer`). 그 문장에만 있는 숫자·기술어는 근거 없는 숫자·용어로 걸리고, 그 문장에만 있는 내용 낱말(두 개, 또는 세 글자 이상 하나)이 수정안에 들어가면 `uncertain_fact_written`으로 보류한다. 묻지 않는다(사용자는 이미 모른다고 답했다). 다음 답에서 확인해 주면 쓸 수 있다.
- "느린 것 같아서 인덱스를 추가했어요"의 "것 같아서"는 이유라 빼지 않는다. "수치는 모르겠는데 캐시는 붙였어요"도 캐시는 확인된 사실이라 "모르겠"만으로는 빼지 않는다.
- 후속 첨삭 안내에 `UNCERTAIN_ANSWER_RULE`과 이번 답의 확신 없는 문장 목록을 붙인다.
- `ABSENCE_STATEMENT`에 "~어 보지 않/못", "안 해·써·만들어 봤"을 넣었다. 대체 수정안은 확신 없는 문장·해 보지 않았다는 문장을 빼고, 받침 ㅆ 끝맺음·해요·돼요·이에요를 "~습니다"체로 바꾼다.
- 개발용 v16x(회귀 확인): 사실 답변 반영 28/28, 막힌 턴 0, 지어낸 것·해 보지 않은 것 적기·요건 over-claim 0, 다듬기 55/55, STAR 행동·결과 88/96, 첫 첨삭 45.5초·후속 10.5초. 이미 적힌 칸 질문 3건은 첫 첨삭 질문이라 이번 변경(후속 첨삭만)과 무관한 흔들림이다.

unseen5로 찾은 결함이라 v16x 확인에 unseen5를 다시 쓰지 않는다. 새 케이스 세트는 더 만들지 않고 여기서 멈춘다.

## 검사하고 다시 쓰기 (resume-v16y)

새 케이스마다 결함이 새 모양으로 나온 까닭은, 서버 검사가 이미 본 모양(숫자 빠짐·기술어 추가·"해 보지 않았다")만 막기 때문이다. 원문 옆에 답을 따로 붙이게 하면 사실이 사라지는 일은 막지만 문장이 매끄럽지 않아 쓰지 않았다(사용자 결정). 대신 매끄럽게 녹여 쓰는 건 그대로 두고, 뜻으로 대조해 틀린 곳만 다시 쓰게 한다(`app/fact_check.py`의 `check_and_repair_revisions`).

1. 후속 첨삭 내용 수정안(변경 폭 0.15 이상, 턴당 4개)을 검사 모델에 동시에 묻는다. 근거로 원문, 같은 항목의 칸, 확인된 답, 확신하지 못한 답 문장을 따로 준다. 찾는 것은 원문 사실이 빠지거나 약해짐(`weakened`), 근거 없는 사실(`unsupported`), 확신하지 못한 답을 단정으로 적음(`kind=uncertain`)이다.
2. 모델이 적은 구절이 원문·수정안에 실제로 있고 근거 글에 그대로 있지 않을 때만 믿는다.
3. 걸리면 그 구절만 짚어 한 번 다시 쓰게 한다(`build_fact_repairer`, reasoning low). 다시 쓴 수정안은 서버 검사(`ground_sentences`·`require_answer_reflection`)와 검사 모델을 다시 통과해야 바꾼다.
4. 그래도 틀리면 근거 없는 사실은 보류(`unsupported_fact`·`uncertain_fact_written`, 묻지 않음)하고, 약해진 사실은 안내(`fact_notice`)만 붙인다. 검사 모델도 틀릴 수 있어 답을 반영한 수정안까지 버리지 않는다.

- 개발용은 이미 고쳐 온 케이스라 검사에 걸린 수정안이 없었다. 괜히 걸려 매끄러운 수정안을 다시 쓰거나 버린 일도 없었다. 반영 못 한 1건은 기존 팀원 범위 검사(`team_scope_exposed`)에 걸린 모델 흔들림이다.
- 다시 쓰기 경로는 실제 모델로 따로 확인했다: 확신 없는 답의 "단위 테스트"를 단정한 수정안을 짚어 "…작성하고 Hardhat으로 테스트넷에 배포했습니다"로 매끄럽게 다시 썼다. 검사 3.2초 + 다시 쓰기·재검사 4.4초 = 7.6초(걸리지 않은 수정안은 1.8초). 걸린 턴만 5~6초 늘어난다.
- 첫 첨삭(39.2초)에는 붙이지 않는다.

## 남은 한계

- 요건 판정의 partial·unconfirmed 경계는 모델 판단이다. 서버는 인용이 원문에 있는지만 본다.
- 요건 정리는 공고 원문 인용을 확인하지만, 공고의 중요한 요건을 빠뜨리는지는 확인하지 못한다(개발용에서 51개 중 5개를 못 찾음).
- 목업 이력서·지어낸 공고로 잰 결과다. 실제 학생 이력서로 확인하지 않았다.
- 기술 요건 질문에 답할 때 항목 이름이 없으면 "어느 항목에서 했는지 확인할 수 없습니다"로 되묻는다. "없음"과 "개인 과제로…"처럼 별도 작업이라고 밝힌 답은 예외로 받는다.
- 수정안이 원문에 한 일로 적힌 기능을 "…하기 위해" 같은 목적 표현으로 바꾸면 그 기능을 했다는 사실이 흐려진다(unseen3 1건). 한국어 표현의 뜻 변화라 낱말 검사로 믿을 만하게 잡지 못해 막지 않았다. 사용자가 적용 전에 확인해야 한다.
- 자기소개서 수정안이 답을 원문 뒤에 "또한 …" 별도 문단으로 붙여 앞 문장과 이어지지 않을 때가 있다.
- 답의 성과 숫자가 자기소개서 칸에만 들어가고, 함께 고친 프로젝트 칸 수정안에는 안 들어갈 때가 있다(숫자의 원래 자리는 프로젝트 칸).
- 항목 이름을 줄여 부르거나 이름 낱말이 겹치는 두 항목을 한 문장에서 말하면 나누지 못할 수 있다(`_split_by_item_mentions`는 이름 전체나 네 글자 이상 이름 낱말이 보일 때만 나눈다).
- 새 프로젝트 제안은 모델이 `new_projects`를 내야 생긴다. 모델이 기존 칸에 끼워 넣기만 하면 서버 검사(숫자·기술어·부정 표현)에 걸리지 않는 한 그대로 나간다.
- 지원 자격 분류는 요건 이름 규칙이다. "백엔드 실무 경험(3년 내외)"처럼 연수가 인용에만 있는 기술 요건은 기술로 둔다. 규칙에 없는 조건(예: 특정 툴 자격증 필수)은 기술 요건으로 남아 질문될 수 있다.
- 문장을 다시 짜면서 한 일이 흐려지는 경우는 검사 모델이 짚어 다시 쓰게 하고, 다시 써도 흐려지면 안내만 붙인다. 검사 모델이 놓칠 때도 있다(unseen4에서 원문 문장이 개선 설명 속에 녹아든 1건을 안내하지 못했다).
- 답에 항목 이름이 없고 별도 경험도 아니면(경력 안의 작은 작업) "어느 항목에서 했는지"를 되묻는다.
- **남은 위험 비율.** 한 번도 안 본 케이스로 잴 때마다 기준 결함(사실이 사라짐·다른 항목에 들어감·지어냄)이 새 모양으로 1~2건 나왔다(unseen~unseen4 각 1건, unseen5 29턴 중 2턴 ≈ 7%). 나온 모양은 모두 서버 검사와 시험으로 막았고, v16y부터는 처음 보는 모양도 검사 모델이 뜻으로 대조해 다시 쓰게 한다. 다만 v16x·v16y는 새 케이스로 확인하지 않았고 검사 모델도 놓칠 수 있어, 턴당 몇 % 수준의 결함이 남아 있을 수 있다(v16w 기준 약 7%보다 낮을 것으로 보지만 재지 않았다). 검사는 턴당 수정안 4개까지만 본다. 목업과 지원자 역할 모델로만 쟀고, 실제 학생 이력서·사람 답변으로는 확인하지 않았다.
- 확신 없는 답 판별은 낱말 규칙이다. "했었나…", "30개였을 걸요"처럼 목록에 없는 말투는 확인된 답으로 본다. 반대로 확신 없는 문장과 확인된 사실이 한 문장에 섞이면(쉼표·"것 같고" 없이) 확인된 사실까지 근거에서 빠져 반영되지 않을 수 있다.
- 첫 첨삭의 명사형 잇기가 만든 기능("~ 조회.")을 한 행동("~을 조회했습니다")으로 바꿀 때가 있다(unseen5 1건, 뒤 대화에서 바로잡힘). 서버 검사는 없다.
- 답을 그대로 붙이는 대체 수정안에는 "그 챗봇" 같은 가리키는 말, 다른 칸에 이미 있는 사실이 남을 수 있다(말투 끝맺음만 바꾼다).
- 새 프로젝트 제안이 경력 칸에 이미 있는 경험을 다시 제안할 때가 있다(겹침 안내는 붙는다).
- STAR 결과 판정은 여전히 흔들린다(unseen3 과대 9). 잘못 "있음"으로 보면 필요한 질문이 걸러진다. 낱말 목록 확인은 처음 보는 표현에서 틀려 넣지 않았다.
