# 이력서 첨삭 속도·품질 기준 측정 (2026-09-28)

## 범위

`evaluation/fixtures/review_cases_dev.json`의 가상 지원자 `backend_entry__fintech` 한 건을 사용했다. 첫 첨삭, 후속 질문 한 번, 누락 점검까지 메모리 저장소로 실행했다. RDS나 실제 학생 이력서의 응답 시간은 측정하지 않았다. 모델 응답의 변동이 있으므로 한 건의 차이는 통계적 결론이 아니다.

| 설정 | 첫 첨삭 | 후속 첨삭 | 전체 | 공고 요건 추출 | 이미 적힌 내용을 재질문 | STAR 행동·결과 일치 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 현재 설정 (medium) | 39.5초 | 14.3초 | 74.2초 | 6.7초 | 0건 | 16/16 |
| 비교 설정 (low) | 33.0초 | 7.0초 | 51.5초 | 5.0초 | 1건 | 16/16 |

`low`는 이 한 건에서 빨랐지만 재질문이 생겼고 STAR 상황·과제 일치도는 15/16에서 12/16으로 낮아졌다. 이 STAR 라벨은 사람이 확정한 정답이 아니므로 참고 지표다. 현재 모델 설정은 변경하지 않았다.

현재 설정의 첫 첨삭 39.5초 중 6.7초는 공고 요건 추출이었다. 공고 요건 캐시는 이미 구현되어 있으므로 이 수치는 캐시가 비어 있는 첫 실행에 해당한다. 나머지 약 32.8초에는 생성 모델과 서버 후처리가 포함된다. 이번 변경부터 응답 `telemetry.generation_ms`로 생성 단계만 따로 기록한다.

## 평가 집계 수정

질문을 `coreCompetencies.text`에서 했지만 확인된 답을 `projects[0].description`에 옮겨 반영한 경우, 기존 평가표는 질문 원래 칸의 수정안만 세어 `positive_answers_with_suggestion=0/1`로 표시했다. 앱에 실제 보이는 수정안을 기준으로 다시 집계하면 `1/1`이다. 최신 원문 인용 일치율과 부정 답변 수정안 집계도 같은 기준으로 맞췄다. 서비스의 첨삭 결과나 화면 계약은 변경하지 않았다.

## 다음 판단 기준

추가 가상 사례에서 첫 첨삭·후속 첨삭의 `generation_ms`, 질문 중복, 사실 보존, 답변 반영을 함께 비교한다. 첫 결과 시간을 줄이더라도 질문·사실 품질이 떨어지는 설정은 적용하지 않는다. 실제 사용자의 지연은 Django 프록시와 RDS 호출을 포함한 별도 측정이 필요하다.
