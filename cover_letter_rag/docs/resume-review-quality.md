# 이력서 첨삭 품질 개선 (resume-v3-quality)

## 범위

기존 이력서 첨삭·적용 API를 유지한다. Flutter, Firestore의 실제 데이터, API 키, 모델 설정은 변경하지 않는다. 추가 모델 호출 없이 기존 생성 결과에 서버 검증을 적용한다.

## 응답 추가 필드

sentence_reviews의 `edit_type`:

- `spelling`: 맞춤법·띄어쓰기
- `tone`: 문체
- `clarity`: 가독성
- `content`: 근거 있는 내용 재구성 (이전 데이터 기본값)
- `none`: 수정 불필요

`validation_issues`는 서버가 채우는 보류 사유 코드다. 모델이 반환한 값은 초기화한다. 기존 `status`는 유지한다. 표현 교정은 formatting, 내용 재구성은 improved, 사실 확인은 needs_confirmation, 유지할 문장은 unchanged다. edit_type 분류는 공백 차이를 제외하면 모델 판단이며, 사실 동등성이 보장되었다는 표시가 아니다.

## 개선 동작

1. 자연스러운 문장은 유지한다. null 수정안 자체를 정보 부족으로 판단하지 않는다.
2. 맞춤법·말투 교정에 수치나 추가 경험을 요구하지 않는다. 진행 중 작업은 진행형을 보존하며 기술 목록은 명사형을 유지한다.
3. 정확히 확인된 original_quote를 기본 근거로 사용한다. 같은 경험의 필드·연결된 답변만 추가 근거로 허용한다.
4. 빈 수정안, 새 수치·기술·역할, 일부 부정·진행 상태·협업 표현 변경, 수치 부호 변경, 개인정보 마스킹 문장 교체를 보류한다.
5. 원문에서 위치를 특정할 수 없는 인용과 이미 채택한 수정 범위에 겹친 수정안은 경고와 함께 제외한다. 비겹침 수정안을 만들도록 프롬프트에도 명시한다.
6. 원문과 동일한 수정안은 제거한다. 실제 확인 질문이 있으면 질문은 유지한다.
7. 검증 문제가 남아 있는 수정안은 적용 API에서도 거부한다.

## 검증과 한계

`tests/test_resume_quality.py`는 고정된 생성 결과를 넣어 서버 검증을 검사하는 오프라인 회귀 테스트다. 실제 LLM의 맞춤법 검출률이나 첨삭 품질을 입증하지 않는다. 역할·부정·상태 검사는 보수적인 문자열 규칙으로, 오탐과 누락이 가능하다. 같은 경험에 등장한 수치라도 다른 지표에 잘못 연결하는 오류, 한국어 의미 변조 전체를 탐지하지는 못한다. 최종 원문·수정안 비교와 사용자 선택이 필요하다.

실제 모델 평가에는 별도 동의된 비식별 이력서를 사용하고 다음 항목을 사람이 대조한다. API 비용이 발생하는 실제 평가와 운영 Firestore 쓰기는 이번 오프라인 검증에 포함하지 않는다.

| 평가 항목 | 통과 기준 |
|---|---|
| 표현 교정 | 오류 수정, 의미·수치·고유명사 보존 |
| 불필요한 수정 | 정상 문장 유지, 기술 목록의 억지 문장화 없음 |
| 사실 보존 | 참여→주도, 예정→완료, 부정→긍정 변경 없음 |
| 내용 보완 | 원문/확인 답변으로 근거 추적 가능 |
| 질문 | 수치 강요 없이 실제 부족한 정보 질문 |
| 공고 활용 | 공고 기술을 지원자 경험으로 추가하지 않음 |
| 재첨삭 | 다른 프로젝트의 답변·수치를 섞지 않음 |

대표 입력에는 오탈자, 구어체, 명사형 목록, 정상 문장, 수치 없는 성과, 진행 중 프로젝트, 팀원 업무, 개인정보, 동일 문장 반복, 공고의 미보유 기술을 포함한다. 원문과 전/후 모델 결과를 같은 조건에서 비교하고 사람의 판정을 기록한 뒤 배포 여부를 정한다.

평가 설계 참고: OpenAI Docs의 [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices). 자동 검사 통과와 사람이 판단하는 유용성을 구분한다.
